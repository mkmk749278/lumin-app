# Firebase Auth Migration — Lumin Android (and Web later)

**Status:** design — pending owner review
**Branch:** `feat/firebase-auth-app`
**Companion:** `mkmk749278/360-v2` branch `feat/firebase-auth-engine`

This document covers the Lumin client side. The engine-side companion
design lives at
`360-v2/docs/firebase_auth_migration.md` and is the canonical source
for the engine API contract referenced below.

---

## Goal

Replace the local HS256 JWT path in `lib/data/auth_service.dart` with
Firebase Authentication. After migration:

- The user signs in via Firebase Phone Auth on Android (Google's SMS
  + SafetyNet/Play Integrity invisible-verification path).
- The "Sign in via Telegram" fallback survives — app calls a new
  engine endpoint to exchange a Telegram-delivered OTP for a Firebase
  custom token, then `signInWithCustomToken` lands a real Firebase
  session.
- The `Authorization: Bearer` header on every engine API call carries
  the Firebase ID token, refreshed automatically by the Firebase SDK.
- Local JWT storage in `flutter_secure_storage` is removed —
  Firebase SDK owns the credential lifecycle.

Web (`app.luminapp.org`, Flutter Web build) follows in a later
session against the same engine endpoints. This PR's design is
Android-first; web is mentioned where conditional shims are needed
but not implemented.

---

## Non-goals (this PR)

- Web build target. Flutter Web compilation, PWA manifest, IndexedDB
  Binance key storage — all deferred to a follow-up PR.
- Binance key management changes. `lib/data/binance_keys_service.dart`
  and the HMAC signing in `lib/data/binance_client.dart` are
  untouched.
- Auto-trade pipeline (`lib/data/auto_trade_watcher.dart`,
  `order_executor.dart`). Unchanged.
- Operator surfaces / 360 CE Ops. Out of scope (different repo).
- UX redesign. The phone → OTP → in flow stays visually identical;
  only the SDK backing it changes.

## What changes

### `pubspec.yaml`

```yaml
dependencies:
  firebase_core: ^3.6.0
  firebase_auth: ^5.3.1
  # Existing dependencies untouched
```

Version range pinned to the latest known-stable as of design date;
PR-code phase confirms compatibility against Flutter
`>=3.24.0 <4.0.0` (already in the pubspec environment block).

### New file: `firebase_options.dart`

Generated by FlutterFire CLI from the Firebase project the owner
creates (see "Owner pre-PR setup" below). Checked into the repo.

Contains the Firebase config (API key, app ID, project ID) for the
Android target. Web + iOS entries added when those targets ship.

> Note on the API key in `firebase_options.dart`: this is a public
> client-side identifier, not a secret. Firebase enforces project
> access via the SHA-256 fingerprint registration on Android and via
> reCAPTCHA on web. Committing it is the documented Firebase
> practice.

### `lib/data/auth_service.dart` (15.9K → ~6K)

Removed:
- `mintAnonymousToken()` (calls deprecated engine `/api/auth/anonymous`)
- `refreshToken()` loop + the `RefreshTimer` it manages
- All `flutter_secure_storage` reads/writes of the local JWT
- The 401-retry-with-fresh-anonymous-token interceptor logic
- Local `JWT` parsing helpers

Added:
- `Future<void> initFirebase()` — calls `Firebase.initializeApp` with
  `DefaultFirebaseOptions.currentPlatform`
- `Stream<User?> authStateChanges` — wraps
  `FirebaseAuth.instance.authStateChanges()`, drives the
  AuthGate / SignInPage routing
- `Future<void> startSmsSignIn(String phoneE164)` — wraps
  `FirebaseAuth.verifyPhoneNumber` with `codeSent` /
  `verificationFailed` / `verificationCompleted` callbacks
- `Future<UserCredential> confirmSmsCode(String verificationId, String code)`
- `Future<void> startTelegramSignIn(String phoneE164)` — POST to
  engine `/api/auth/telegram-otp/issue`
- `Future<UserCredential> confirmTelegramCode(String phoneE164, String code)` —
  POST to engine `/api/auth/telegram-otp/verify`, receives custom
  token, calls `FirebaseAuth.instance.signInWithCustomToken(...)`
- `Future<String?> currentIdToken({bool forceRefresh = false})` —
  thin wrapper for the HTTP client

### `lib/data/api_client.dart`

Single change: the `Authorization` header source.

Before:
```dart
final token = await _authService.getLocalJwt();
options.headers['Authorization'] = 'Bearer $token';
```

After:
```dart
final token = await _authService.currentIdToken();
if (token != null) {
  options.headers['Authorization'] = 'Bearer $token';
}
```

The dio retry interceptor on 401 calls
`currentIdToken(forceRefresh: true)` once before giving up — handles
the rare case where the cached token expired between the SDK's
auto-refresh cycles.

### `lib/data/repository.dart` (34.4K)

No structural changes — it consumes `ApiClient` and `AuthService`
through the existing surface. A few `await _auth.getLocalJwt()`
replaced with `await _auth.currentIdToken()` if any direct calls
remain (PR-code phase audits).

### `lib/features/auth/pages/` (sign-in screens)

UX unchanged. Wiring rewired:

- `PhoneInputPage`:
  - "Send via SMS" → `authService.startSmsSignIn(phoneE164)`
  - "Send via Telegram" → `authService.startTelegramSignIn(phoneE164)`
- `OtpCodePage`:
  - SMS path → `authService.confirmSmsCode(verificationId, code)`
  - Telegram path → `authService.confirmTelegramCode(phoneE164, code)`
- `SignupPage` (post-first-signin profile collection) — unchanged;
  uses the existing `PUT /api/profile` endpoint, now authorized via
  Firebase ID token

### `main.dart`

Adds `await Firebase.initializeApp(...)` before `runApp`. The
existing splash → AuthGate flow stays; AuthGate now subscribes to
`FirebaseAuth.authStateChanges()` instead of polling a local-JWT
expiry timestamp.

## CI / build pipeline — google-services.json injection

The `android/` folder is **not** committed to the repo (verified —
`.gitignore` doesn't exclude it but `flutter create --platforms=android .`
runs in `build-apk.yml` at build time and regenerates it). The
`google-services.json` for the Firebase Android app therefore cannot
be a checked-in file; it must be injected by CI.

### `build-apk.yml` changes

After the `flutter create --platforms=android .` step and before
`flutter build apk`:

```yaml
- name: Inject google-services.json
  env:
    GOOGLE_SERVICES_JSON: ${{ secrets.GOOGLE_SERVICES_JSON }}
  run: |
    mkdir -p android/app
    echo "$GOOGLE_SERVICES_JSON" > android/app/google-services.json

- name: Patch android/build.gradle for Google services plugin
  run: |
    # Idempotent classpath insertion
    sed -i '/classpath ''com.android.tools.build:gradle/a \        classpath '\''com.google.gms:google-services:4.4.2'\''' android/build.gradle

- name: Patch android/app/build.gradle for plugin apply
  run: |
    # Append apply plugin line if not present
    grep -q "com.google.gms.google-services" android/app/build.gradle || \
      echo "apply plugin: 'com.google.gms.google-services'" >> android/app/build.gradle
```

`GOOGLE_SERVICES_JSON` is a GitHub Actions secret containing the file
contents — owner uploads the file via Repo Settings → Secrets and
Variables → Actions after Firebase project creation.

### Alternative considered

Move the patching logic into a `tools/prepare_android_build.sh`
script in the repo (lives alongside any future android-prep needs),
and have the workflow just invoke it. Cleaner separation; PR-code
phase decides between inline-in-yml vs script-in-repo based on what
the rest of `build-apk.yml` looks like.

### What stays in CI

- The signed APK release flow (keystore from secrets) — unchanged
- The GitHub Release publish step — unchanged
- The version-bump check on `pubspec.yaml` — unchanged

## Transition strategy on the client

Per owner call: feature-flag both auth modes during transition on the
engine side. **The Lumin app itself does NOT need dual-mode logic
during the transition window** — the new APK version (e.g. `0.1.0+23`,
post-Firebase) only knows Firebase; the old APK version (`0.0.22+22`,
pre-Firebase) only knows local HS256. The engine accepts both, so
each app version on each tester's phone works against the same engine
deployment.

This is simpler than client-side dual-mode and matches the engine's
feature-flag plan:

1. Engine ships with `FIREBASE_AUTH_ENABLED=false` (no-op deploy)
2. Owner creates Firebase project + drops service account JSON on VPS
3. Owner flips `FIREBASE_AUTH_ENABLED=true`, restarts engine
4. New Lumin APK ships (this PR, after code phase + review + merge)
5. Testers update — phones run Firebase Phone Auth; engine
   transparently backfills `firebase_uid` on their existing user row
6. After ~1 week, owner confirms via engine logs / users-table query
   that every tester has `firebase_uid` populated
7. Follow-up PR strips legacy HS256 from engine + drops the
   transition shims

## Cross-platform considerations (preview for web PR)

The following are non-trivial conditional shims that web will need;
this Android-first PR sets them up cleanly so the web port is a small
delta:

| Code path | Android | Web |
|---|---|---|
| `firebase_auth.verifyPhoneNumber` | Uses Play Integrity (or reCAPTCHA fallback) | Uses reCAPTCHA verifier (web-only API surface — `RecaptchaVerifier`) |
| `flutter_secure_storage` (Binance keys) | Android Keystore-backed | IndexedDB + passphrase-derived AES (different module — `flutter_secure_storage_web`) |
| `package_installer` (APK self-update) | Used | N/A — web auto-updates on next page load |
| `permission_handler` (notifications, etc.) | Native | Web Push API where supported |
| Platform-detection guards (`kIsWeb`) | New `if (kIsWeb)` branches where above paths diverge | New branches |

This PR does not introduce these branches — they're noted so that the
auth service rewrite leaves natural seams (e.g. `verifyPhoneNumber`
takes a `RecaptchaVerifier?` parameter that's null on Android).

## Risks

| Risk | Mitigation |
|---|---|
| `google-services.json` committed accidentally | Add `android/app/google-services.json` to `.gitignore`; rely on CI injection only |
| Existing testers see a "verify your number again" flow on first new-APK launch | Expected and acceptable. The engine backfills `firebase_uid` on the matching phone row, so all their data (tier, Binance keys binding, settings) is preserved. Surface a one-line "Sign in to continue" copy on the splash. |
| Firebase Phone Auth `auth/missing-app-credential` on first build | Owner registers the APK's release-keystore SHA-256 fingerprint in Firebase Console (required). Debug-keystore fingerprint also registered for local dev. |
| reCAPTCHA challenge appears on some Android devices (Play Integrity unavailable) | Standard Firebase behavior; SDK shows the challenge inline. No code change needed. |
| Phone-number formatting mismatch between app and engine | `phone_e164` is already E.164 in the engine. App uses the existing `country_codes.dart` helper to format. No new normalization needed. |
| `flutter_secure_storage` orphaned reads (old JWT entries) | One-shot cleanup on first post-migration launch: `secure_storage.delete(key: 'jwt_token')`. Tiny code path, runs idempotent. |
| In-app APK auto-update interaction with Firebase init | `Firebase.initializeApp` is called from `main()` before splash; APK self-update happens later via `UpdateService`. No interaction. |

### Manual verification on a tester device

1. Install post-migration APK over pre-migration APK (tester's phone
   already has a session via local JWT)
2. Launch app → AuthGate sees no Firebase user, routes to SignInPage
3. Tap "Send via SMS" with the tester's phone number → Firebase
   delivers code → enter → land in app
4. Verify in engine logs that `firebase_uid` was backfilled on the
   tester's existing `user_id` row
5. Verify tier, paid_until, Binance keys binding all preserved
6. Sign out → sign in via "Send via Telegram" → same `user_id`
   reached, custom-token bridge works
